# Build: Gov Service Research Tool (standalone)

## Scope (read this first)
This is for **Bihar state services + Central/national government services only** — not nationwide/all-states. I'm building Onix for Bihar first. Do not design for other states.

## Goal
A standalone tool, given a service name + scope I've already chosen (e.g. "Ration Card" + "Bihar", or "PAN Card" + "Central"), that researches it and outputs a structured, source-linked record — ready for my review before I paste/save it into my admin panel. Must be fully decoupled from my main app ("Onix") — separate codebase, separate deployment, separate database. I will import its output into Onix myself later; do not write directly to Onix's database or codebase.

## Deployment (important — I develop on a mobile phone, not a laptop)
- I use Pydroid 3 on Android for my main app, which CANNOT run Playwright (needs real browser binaries) or Tesseract OCR (needs system-level binaries) — Pydroid's sandbox doesn't support either.
- So: deploy this tool to Render (same as I do for Onix), free tier, as its own separate service with its own separate Render app/repo.
- I will trigger and use it entirely from my phone's browser, hitting the deployed URL — so the review UI needs to be simple, mobile-responsive, and usable on a small screen.
- Build step must explicitly install Playwright's Chromium browser (`playwright install --with-deps chromium` or equivalent) as part of the Render build — don't assume it's preinstalled.
- Be upfront that free-tier Render has cold starts (30-60s if idle) and limited RAM/CPU — a full research run (search + crawl + PDF/OCR + Playwright + LLM merge) may realistically take 1-3 minutes, not seconds. That's fine, just don't silently design around an unrealistic speed assumption.
- If Playwright's memory footprint becomes a real problem on Render's free tier, tell me — the fallback is to run the browser-automation step less aggressively (e.g. only for photo/signature spec confirmation) rather than dropping it entirely.

## How I'll actually use it
I already have an admin panel where I click "Add Service," pick a scope (Bihar / Central) from a dropdown, type/select a service name, and fill in a form (see attached `admin_dashboard.html`). This tool is NOT a replacement search UI — it's a research assistant that takes the same two inputs (service name + scope) and pre-fills what that form needs, so I copy/paste or eventually auto-fill instead of manually digging for 30+ minutes.

## Non-negotiables
- Standalone repo/folder. No dependency on Onix's code or DB.
- Output format must match the schema below exactly (this is Onix's real `service_knowledge` table, see attached `database.py`).
- Every field must carry a source URL where it was found.
- **Do NOT have the LLM invent a confidence score.** My real system (`knowledge.py`, attached) already auto-computes `confidence_score` server-side from field completeness — a weighted checklist (department, portal_name, portal_url, eligibility, fees, timeline, validity, category, documents, steps, sources, photo_size, signature_size, upload_limits, notes, last_verified all contribute; missing fields just contribute 0). Your tool should output the same raw fields; confidence scoring happens automatically on my side when I save. Instead, your tool should flag **per-field** whether it found the data or not (found / not found / uncertain) so I know what to double check — that's the actual signal I need from you, not a made-up number.
- Whitelist domains only (list below) — no open web crawling outside it.
- All free/local tools only, except one LLM call per service for the merge step — I have a **Gemini API key**, use the Gemini API (not OpenAI).
- I'm ready to manually review a portion of fields myself — the tool's job is to get me most of the way there accurately, not claim full automation.

## Target output schema (must match field-for-field — maps directly to my admin panel's Add/Edit Service form)
```
service_key            TEXT     -- kebab-case slug of service_name, e.g. "ration-card"
service_name           TEXT     -- e.g. "Ration Card"
state                  TEXT     -- "Bihar" or "Central" (exact scope I gave you)
jurisdiction_type      TEXT     -- "state" if Bihar, "central" if Central
category               TEXT     -- e.g. "Certificates", "Identity", "Welfare & Employment", "Travel"
icon                   TEXT     -- leave blank, I'll pick this myself
department             TEXT
portal_name            TEXT
portal_url             TEXT
apply_url              TEXT
documents               ARRAY of strings, e.g.
                        ["Aadhaar Card (mandatory for identity/OTP verification)", "Passport-size photograph"]
eligibility             TEXT
fees                    TEXT
timeline                TEXT
photo_size              TEXT    -- exact dimensions/specs if found
signature_size          TEXT
upload_limits            TEXT
validity                TEXT
steps                   ARRAY of strings, ordered, e.g.
                        ["Open ServicePlus Bihar.", "Open the Income Certificate form.", ...]
notes                   TEXT
sources                 ARRAY of URLs actually used
manual_review_needed    BOOLEAN -- true if any key field (department, portal_url, eligibility, fees, timeline, documents, steps) came back empty or uncertain
field_status             OBJECT mapping each field name above to "found" / "not_found" / "uncertain" — this is your confidence signal, not a numeric score
last_verified            TEXT (ISO date, when this research run happened)
```
Note: leave `confidence_score` out entirely — computed automatically by my backend on save, not by your tool.

## Pipeline I want
1. **Input**: I give it a service name + scope (Bihar or Central) — this mirrors what I already select in my admin panel, not a new search feature.
2. **Discovery**: search only within the whitelist above. No general web crawling outside it.
3. **Extraction**:
   - HTML: scrape tables/lists for eligibility, documents, fees.
   - PDFs: direct text extraction if text-based; OCR (Tesseract) if scanned/image PDF.
   - Photo/signature specs: check PDFs and images specifically, since these are often diagrams, not text.
   - Browser automation (Playwright): open the actual "Apply Online" form to confirm required fields, photo/signature specs, and steps — often the only accurate source for these.
4. **Merge**: one Gemini API call normalizes everything into the schema above, and marks per-field status (found/not_found/uncertain) with a source URL per field.
5. **Review UI**: simple local web page (or CLI table) showing each field, its status, and source link, with an approve/edit action before final save.
6. **Storage**: tool's own local SQLite/JSON file — NOT Onix's `agent.db`. Export as JSON matching the schema above.
7. **Re-verify mode**: given an existing record, re-run discovery+extraction, diff against the old record, show only what changed.

## Integration plan (for later — don't build this part yet)
- Tool exposes a `export_to_onix_format()` function or a `/export` JSON endpoint returning records shaped like the schema above.
- I will write a small separate import script inside Onix later that reads this JSON and calls my existing `save_service_knowledge()` function (in `knowledge.py`) by `service_key`. Do not touch Onix files or try to wire this up yourself.
